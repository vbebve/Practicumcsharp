# Practicum — Event Management API

## Описание проекта

Данный проект был разработан в рамках учебной программы Practicum. Целью первого спринта было знакомство с платформой ASP.NET Core и основами разработки Web API.

В рамках проекта реализовано REST API для управления мероприятиями (Events), поддерживающее основные CRUD-операции, фильтрацию, пагинацию и обработку ошибок.

### Цели проекта

1. Познакомиться с платформой ASP.NET Core.
2. Научиться использовать базовые CRUD-операции.
3. Изучить принципы Dependency Injection (DI).
4. Научиться тестировать приложение через Swagger.
5. Освоить написание unit-тестов.
6. Реализовать фильтрацию и пагинацию данных.

## Используемые технологии

- ASP.NET Core Web API (.NET 8).
- Dependency Injection (DI).
- Swagger / Swashbuckle.
- DTO (Data Transfer Objects).
- LINQ.
- xUnit — модульное тестирование.
- Middleware — глобальная обработка исключений.

## Структура проекта

Основные компоненты приложения:

1. **Controllers** — обработка HTTP-запросов и формирование HTTP-ответов.
2. **DTOs** — модели передачи данных между клиентом и API.
3. **Interfaces** — интерфейсы сервисов.
4. **Models** — внутренние модели данных приложения.
5. **Realizations** — реализации бизнес-логики.
6. **Middleware** — промежуточное ПО для глобальной обработки исключений.

## Модель мероприятия (Event)

Модель мероприятия содержит следующие свойства:

| Свойство | Описание | Тип |
|---|---|---|
| ID | Уникальный идентификатор события. Присваивается автоматически. | int |
| Title | Название мероприятия. Обязательное поле. | string |
| Description | Описание мероприятия. Необязательное поле. | string? |
| StartAt | Дата и время начала мероприятия. | DateTime |
| EndAt | Дата и время окончания мероприятия. Должна быть позже StartAt. | DateTime |

Входящие данные проверяются с помощью DTO и механизмов валидации.

## API Endpoints

| Метод | Endpoint | Описание |
|---|---|---|
| GET | `/events` | Получение списка мероприятий с фильтрацией и пагинацией |
| GET | `/events/{id}` | Получение мероприятия по ID |
| POST | `/events` | Создание нового мероприятия |
| PUT | `/events/{id}` | Изменение существующего мероприятия |
| DELETE | `/events/{id}` | Удаление мероприятия |

## Фильтрация и пагинация

Для получения списка мероприятий (`GET /events`) предусмотрены следующие query-параметры:

| Параметр | Тип | Значение по умолчанию | Описание |
|---|---|---|---|
| title | string | — | Поиск мероприятий по названию |
| startAt | DateTime | — | Фильтрация по дате начала: StartAt не раньше указанной даты |
| endAt | DateTime | — | Фильтрация по дате окончания: EndAt не позже указанной даты |
| page | int | 1 | Номер страницы |
| pageSize | int | 10 | Количество мероприятий на одной странице |

Все параметры необязательные. Фильтры можно комбинировать.

Поиск по названию выполняется без учёта регистра. При одновременном использовании нескольких фильтров мероприятие должно соответствовать всем указанным условиям.

Если `page` или `pageSize` меньше 1, сервис использует значения 1 и 10 соответственно.

### Примеры запросов

Получение всех мероприятий:

```http
GET /events
```

Поиск по названию:

```http
GET /events?title=conference
```

Фильтрация по датам:

```http
GET /events?startAt=2026-11-15&endAt=2026-11-30
```

Пагинация:

```http
GET /events?page=2&pageSize=5
```

Комбинированная фильтрация:

```http
GET /events?title=conference&startAt=2026-11-15&endAt=2026-11-30&page=1&pageSize=10
```

### Формат ответа с пагинацией

Метод `GET /events` возвращает объект `PaginatedResult`, содержащий:

- `TotalCount` — общее количество мероприятий, соответствующих фильтрам.
- `Items` — список мероприятий текущей страницы.
- `Page` — номер текущей страницы.
- `PageSize` — количество элементов на странице.

Пример ответа:

```json
{
  "totalCount": 25,
  "items": [
    {
      "id": 1,
      "title": "C# Conference",
      "description": "Programming conference",
      "startAt": "2026-11-15T10:00:00",
      "endAt": "2026-11-15T18:00:00"
    }
  ],
  "page": 1,
  "pageSize": 10
}
```

В примере показан один элемент массива `items`; фактическое количество элементов зависит от результатов фильтрации и размера страницы.

## Архитектура и обработка данных

Проект использует принцип разделения ответственности:

1. Контроллер принимает HTTP-запросы, получает query-параметры и преобразует входящие DTO во внутренние модели.
2. Сервис `EventService` выполняет бизнес-логику и управляет коллекцией мероприятий.
3. Интерфейс `IEventService` определяет контракт взаимодействия контроллера с сервисом.
4. Dependency Injection обеспечивает внедрение реализации сервиса.
5. LINQ используется для фильтрации, подсчёта и пагинации мероприятий.

Для хранения данных используется коллекция `List<Event>` в оперативной памяти приложения. После перезапуска приложения созданные мероприятия удаляются.

## Обработка ошибок

Для централизованной обработки необработанных исключений реализован `GlobalExceptionHandlingMiddleware`.

Middleware перехватывает исключения, записывает информацию о них в лог и возвращает клиенту JSON-ответ с соответствующим HTTP-статусом.

### Соответствие исключений HTTP-статусам

| Исключение | HTTP-статус | Описание |
|---|---|---|
| ValidationException | 400 Bad Request | Ошибка валидации данных |
| ArgumentException | 400 Bad Request | Некорректный аргумент |
| UnauthorizedAccessException | 403 Forbidden | Доступ запрещён |
| KeyNotFoundException | 404 Not Found | Запрашиваемый ресурс не найден |
| Другие исключения | 500 Internal Server Error | Внутренняя ошибка сервера |

### Формат ответа при ошибке

При обработке исключения middleware возвращает объект `ProblemDetails`.

Пример ответа:

```json
{
  "status": 400,
  "detail": "Описание ошибки"
}
```

При возникновении ошибок валидации входящих DTO контроллер с атрибутом `[ApiController]` также может автоматически вернуть ответ `400 Bad Request` с описанием ошибок валидации.

Полная информация об исключениях записывается в лог приложения.

## Unit-тестирование

Для проверки бизнес-логики сервиса `EventService` используется библиотека **xUnit**.

Тесты расположены в отдельном проекте `PracticumTests`.

Проверяются следующие сценарии:

**Успешные сценарии:**
- Создание мероприятия.
- Получение всех мероприятий.
- Получение мероприятия по ID.
- Обновление существующего мероприятия.
- Удаление существующего мероприятия.
- Фильтрация по названию.
- Фильтрация по датам начала и окончания.
- Пагинация мероприятий.
- Комбинированная фильтрация.

**Неуспешные сценарии:**
- Получение мероприятия с несуществующим ID.
- Обновление мероприятия с несуществующим ID.
- Проверка поведения при некорректных данных.
- Проверка поведения при некорректных датах.

### Запуск тестов

Из корневой директории решения выполните команду:

```bash
dotnet test
```

Команда выполнит сборку тестового проекта, запустит тесты и выведет результаты их выполнения.

## Запуск проекта

### Требования

1. Установленный .NET SDK версии 8.0 или выше.
2. Git для клонирования репозитория.

### Клонирование репозитория

```bash
git clone https://github.com/vbebve/Practicumcsharp
cd Practicum
```

### Восстановление зависимостей

```bash
dotnet restore
```

### Сборка проекта

```bash
dotnet build
```

### Запуск приложения

```bash
dotnet run
```

После запуска API доступно по локальному адресу, указанному в консоли. Документация и тестирование endpoints доступны через Swagger UI.

## Swagger

Swagger используется для просмотра документации API и отправки HTTP-запросов без необходимости использовать сторонние HTTP-клиенты.

После запуска приложения откройте адрес:

```text
https://localhost:<port>/swagger
```

Вместо `<port>` укажите порт, указанный в консоли при запуске приложения.
